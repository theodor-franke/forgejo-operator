# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

forgejo-operator is a Kubernetes operator, scaffolded with Kubebuilder v4 (go.kubebuilder.io/v4 layout) via `operator-sdk create api` (available on `PATH`; that's the "operator-cli" for this project — use it to scaffold any further CRD/controller pairs rather than hand-writing the boilerplate), that **configures an already-running Forgejo instance** — it does not deploy or manage the Forgejo server itself. It has five CRDs (group `forgejo.schranke.de`, version `v1alpha1`):

- `Forgejo` — cluster-scoped. Points at an existing Forgejo server (`spec.url` + `spec.authRef` credentials) and its reconciler calls the server's info endpoint (`/api/v1/version`) to record the version in status. Optionally, `spec.defaultPullKeySecretRef` names a Secret holding a shared SSH deploy-key pair to hand out to every repository on this instance (see `ForgejoRepository` below); if that Secret doesn't exist yet, the reconciler generates one (`internal/sshkey`, `internal/controller/pullkey.go`) using `spec.sshHost`/`spec.sshPort` (defaulting to `spec.url`'s hostname and port 22) to discover the instance's real SSH host key for `known_hosts`. `spec.base` is the externally reachable base URL of the Flux notification-controller webhook receiver endpoint on this cluster, needed only if `ForgejoWebhook` (below) is used against this instance.
- `ForgejoOrganization` — namespaced. References a `Forgejo` instance by name (`spec.instanceRef.name`, cluster-scoped so no namespace needed) and its reconciler creates/updates a matching organization *and* its `spec.teams` on that server via the real Forgejo REST API. The organization's name on Forgejo is the CR's own `metadata.name`; same for each team — note that since the CR is namespaced but the remote Forgejo org name is not, two `ForgejoOrganization`s with the same name in different namespaces both targeting the same instance would otherwise collide on the same remote org. A validating webhook (`internal/webhook/v1alpha1/forgejoorganization_webhook.go`) rejects exactly that on create/update — see "Webhook" below. A team's access mirrors Forgejo's own two mutually-exclusive team modes: `accessMode: admin` (full admin on every repo feature) or the default `accessMode: custom`, where `repoPermissions` sets `none`/`read`/`write` independently per feature (`code`, `issues`, `pullRequests`, `releases`, `wiki`, `projects`, `packages`, `actions` — exactly the table Forgejo's own team edit page shows). Each team's `groups` (IdP-claimed group names) are aggregated, across every `ForgejoOrganization` in any namespace targeting the same instance, into that instance's "map claimed groups to organization teams" OAuth2 setting — see `internal/forgejoweb` below, since that one setting has no REST API.
- `ForgejoActionSecret` — namespaced. References a `ForgejoOrganization` by name (`spec.organizationRef.name`) **in the same namespace** — there's no cross-namespace ref field — and upserts a Forgejo Actions secret (`spec.name`, e.g. `DOCKER_PASSWORD`) on it, sourcing the value from a key in a Kubernetes `Secret` (`spec.valueFrom`, which *can* point at a different namespace via `valueFrom.secretNamespace`, unlike the organization ref). Forgejo's Actions secrets are write-only — the API never returns a value, only names — so there's no drift to detect; every successful reconcile just re-applies the current source value unconditionally. Forgejo also uppercases whatever secret name is sent, regardless of the case used in `spec.name`.
- `ForgejoRepository` — namespaced. References a `ForgejoOrganization` by name (`spec.organizationRef.name`, same-namespace, same convention as `ForgejoActionSecret`) and creates/updates a repository under it. The repository's name on Forgejo is the CR's own `metadata.name`. `spec.autoInit` (create an initial commit) and `spec.defaultBranch` only take effect at creation time — a repo created with `autoInit: false` has no default branch until something is pushed to it, and `EditRepo` has no `auto_init` field at all. `spec.description`/`private`/`template`/`defaultBranch` are all live-editable and reconciled on every pass via `EditRepo`. If the instance has `defaultPullKeySecretRef` set, the reconciler also adds that instance's shared public key as a read-only deploy key (title `forgejo-operator-default-pull-key`, matched by title on later reconciles so it isn't re-added) — set `spec.optOutDefaultPullKey: true` to skip (or remove, if toggled after the fact) that on a specific repo.
- `ForgejoWebhook` — namespaced. Creates a repository webhook on Forgejo that delivers events to a Flux `notification.toolkit.fluxcd.io/v1` `Receiver`, integrating this operator with Flux's push-to-reconcile flow. The target repository is set via exactly one of `spec.repositoryRef` (a `ForgejoRepository` by name, same-namespace convention) or `spec.repository` (`instanceRef` + a repository web `url`, for repositories this operator doesn't otherwise manage) — a `+kubebuilder:validation:XValidation` CEL rule on the spec enforces the exactly-one-of constraint at admission time, no webhook needed. `spec.receiverRef` (`name`+`namespace`, always both required since a Receiver commonly lives in a different namespace, e.g. `flux-system`) is **always** required: the Receiver's `status.webhookPath` is combined with the target `Forgejo` instance's `spec.base` into the webhook's target URL, and the Secret its `spec.secretRef.name` points at (read from the Receiver's own namespace, key `token` — Flux's own convention) becomes the webhook's shared signing secret. `spec.type` defaults to `"forgejo"` (Forgejo is a Gitea fork and shares Gitea's webhook signature format, which is what Flux's `"gitea"` Receiver type expects); `spec.events` defaults to `["push"]`; `spec.suspend` disables the webhook on Forgejo without deleting it. Reconcile matches an existing webhook by its `config.url` (stable per-object, since a ForgejoWebhook has a 1:1 relationship with its target URL) rather than trusting `status.hookID`, mirroring `pullkey.go`'s match-by-title idiom for deploy keys.

`Forgejo` is cluster-scoped (`+kubebuilder:resource:scope=Cluster`); `ForgejoOrganization`, `ForgejoActionSecret`, `ForgejoRepository`, and `ForgejoWebhook` are namespaced (ordinary CRDs, no scope marker). Every `Secret` referenced from a cluster-scoped or cross-namespace spot is looked up via an explicit `secretNamespace` field alongside the name (`spec.authRef`, `spec.valueFrom`) — `resolveOrganization`/`resolveInstance`/`resolveRepository` in `internal/controller/instance.go` is where namespace vs. cluster-scoped lookups actually diverge, see below.

## Common commands

All common tasks are exposed via the `Makefile` (run `make help` for the full list with descriptions).

- Build the manager binary: `make build` (runs `manifests generate fmt vet` first, outputs to `bin/manager`)
- Run the controller locally against the current kubeconfig context: `make run`
- Run unit/integration tests (envtest + a real Forgejo instance): `make test` — **requires Docker**, see "Testing" below. There is no separate e2e suite: the controller tests already start a real Forgejo container and drive it through the real API, which is what an e2e suite would otherwise do.
  - Run a single test/package directly once envtest assets exist: `KUBEBUILDER_ASSETS="$(bin/setup-envtest use <k8s-version> --bin-dir "$(pwd)/bin" -p path)" go test ./internal/controller/... -run TestControllers -v` (swap in `./internal/webhook/v1alpha1/... -run TestAPIs` for the webhook suite; use an absolute `--bin-dir`, or `KUBEBUILDER_ASSETS` resolves to a relative path and fails outside the Makefile)
  - Both suites use Ginkgo/Gomega and boot their own `envtest.Environment` (`internal/controller/suite_test.go`, `internal/webhook/v1alpha1/webhook_suite_test.go`) — adding specs means adding Ginkgo `Describe`/`It` blocks, not plain `Test*` functions, to the relevant one.
- Lint: `make lint` (golangci-lint), autofix: `make lint-fix`, verify lint config: `make lint-config`
- Regenerate CRD manifests / RBAC from kubebuilder markers: `make manifests`
- Regenerate DeepCopy/runtime.Object code from kubebuilder markers: `make generate`
- Format/vet only: `make fmt`, `make vet`

`make test` and `make build` both depend on `manifests generate fmt vet`, so generated code and CRD YAML stay in sync automatically — you rarely need to invoke `make manifests`/`make generate` standalone unless iterating quickly on API types.

### Deployment (against a real/kind cluster)

Two independent paths — pick one, they're not meant to be combined:

- **Kustomize**: `make install` (apply CRDs) → `make deploy IMG=<registry>/forgejo-operator:tag` (deploy the manager) → `make undeploy` / `make uninstall` to tear down. `make docker-build docker-push IMG=...` builds/pushes the image first (multi-arch via `make docker-buildx`).
- **Helm**: `make helm-deploy IMG=<registry>/forgejo-operator:tag` installs/upgrades `dist/chart` as release `forgejo-operator` in namespace `forgejo-operator-system` (both configurable via `HELM_RELEASE`/`HELM_NAMESPACE`). `make helm-uninstall`, `make helm-status`, `make helm-history`, `make helm-rollback` round out the lifecycle. cert-manager must already be installed in the cluster — it's a hard requirement of the chart, not a toggle (see "Distribution" below).

## Architecture

Standard Kubebuilder v4 layout — the pieces that matter for making changes:

- `api/v1alpha1/forgejo_types.go` — the `Forgejo` CRD Go type (`ForgejoSpec`, `AuthSecretRef`, `PullKeySecretRef`, `ForgejoStatus`). Source of truth for the CRD schema; `+kubebuilder:...` markers here drive both codegen (`make generate` → `zz_generated.deepcopy.go`) and manifest generation (`make manifests` → `config/crd/bases/*.yaml`). Edit this file, then regenerate — don't hand-edit the generated CRD YAML or `zz_generated.deepcopy.go`.
- `api/v1alpha1/forgejoorganization_types.go` — the `ForgejoOrganization` CRD Go type (`ForgejoOrganizationSpec` with `InstanceRef`/`Visibility`/`AdminPermissionRights`/`Teams`, `ForgejoOrganizationStatus`). `Team` carries `Name`, `Description`, `Groups`, `AccessMode` (`custom`/`admin`), `RepoPermissions` (per-feature `none`/`read`/`write`), `CanCreateOrgRepo`, `IncludesAllRepositories`. Same codegen rules apply.
- `api/v1alpha1/forgejoactionsecret_types.go` — the `ForgejoActionSecret` CRD Go type (`ForgejoActionSecretSpec` with `OrganizationRef`/`Name`/`ValueFrom`, `ForgejoActionSecretStatus`; `OrganizationRef` is also reused as-is by `ForgejoRepositorySpec`). `Name` is validated with `+kubebuilder:validation:Pattern` (`^[A-Za-z_][A-Za-z0-9_]*$`) to match what Forgejo actually accepts (verified against a live instance: no hyphens, must start with a letter/underscore; case doesn't matter since Forgejo uppercases it server-side).
- `api/v1alpha1/forgejorepository_types.go` — the `ForgejoRepository` CRD Go type (`ForgejoRepositorySpec` with `OrganizationRef`/`Description`/`Private`/`Template`/`AutoInit`/`DefaultBranch`/`OptOutDefaultPullKey`, `ForgejoRepositoryStatus`).
- `api/v1alpha1/forgejowebhook_types.go` — the `ForgejoWebhook` CRD Go type (`ForgejoWebhookSpec` with `RepositoryRef`/`Repository`/`ReceiverRef`/`Type`/`Events`/`BranchFilter`/`Suspend`, `ForgejoWebhookStatus` with `URL`/`HookID`). Carries the `+kubebuilder:validation:XValidation` CEL rule enforcing exactly one of `RepositoryRef`/`Repository`.
- `internal/sshkey/sshkey.go` — pure Go SSH keypair generation and host-key discovery (no shelling out to `ssh-keygen`/`ssh-keyscan`), built on `golang.org/x/crypto/ssh` (+`ssh/knownhosts`). `Generate` makes an ed25519 pair in OpenSSH authorized_keys/PEM text form. `ScanHostKey` opens a real TCP+SSH connection and aborts the handshake (via a `HostKeyCallback` that captures the offered key and returns a sentinel error) the instant the server offers its host key — no credentials are needed since host keys are exchanged before authentication.
- `internal/controller/pullkey.go` — shared by the `Forgejo` and `ForgejoRepository` reconcilers. `ensureDefaultPullKeySecret` creates the Secret (fields `publicKey`/`privateKey`/`knownHosts`) if `Spec.DefaultPullKeySecretRef` is set and it doesn't exist yet; does nothing if it already exists (no drift repair) or if the ref is unset. `reconcileDefaultPullKey` is the `ForgejoRepository`-side half: lists deploy keys, finds one by the fixed title `forgejo-operator-default-pull-key`, and creates/deletes it to match `spec.optOutDefaultPullKey` (no-op if the instance has no default pull key configured).
- `internal/forgejoapi/client.go` — a small, dependency-free REST client for the subset of the real Forgejo API this operator needs (`GetVersion`, org/team/Actions-secret/repository/deploy-key CRUD), authenticated with HTTP basic auth. `ErrNotFound` signals a 404; everything else non-2xx comes back as `*APIError`. The `UnitXxx` constants (`UnitCode`, `UnitIssues`, ...) are the `units_map` keys Forgejo's team API expects. **Gotcha verified against a live instance**: a team's `units_map` is only applied when the *same* edit/create request's `permission` is not `"admin"` — if a team is currently in admin mode, sending `units_map` alone (without also setting a non-admin `permission`) is silently ignored and the team stays admin. `internal/controller/forgejoorganization_controller.go`'s `teamAccessArgs` always sends both together for exactly this reason. `UpsertOrgActionSecret` is a single idempotent `PUT` (201 create / 204 update, both success) — unlike organizations/teams/repos there's no separate create-vs-edit branch needed. `CreateRepoOptions` has `AutoInit`; `EditRepoOptions` deliberately doesn't — Forgejo's edit-repo API has no such field, it's create-only. Deploy keys have **no edit endpoint at all** (create or delete-and-recreate only); `CreateDeployKey` returns 422 if a key with that exact content is already registered on the repo (so callers must `ListDeployKeys` first to stay idempotent, unlike `UpsertOrgActionSecret`); `DeleteDeployKey` is already idempotent server-side (204 even when the key is already gone), unlike most other Forgejo delete endpoints, which 404. Repository webhooks (`Hook`/`CreateRepoHook`/`EditRepoHook`/`ListRepoHooks`/`DeleteRepoHook`) follow the same shape as deploy keys: no single upsert call, so `ForgejoWebhookReconciler` lists first and matches by `config["url"]` to decide create-vs-edit. This is the only place that talks REST to Forgejo.
- `internal/forgejoweb/client.go` — a session-based (login form + CSRF + cookie jar) client that drives Forgejo's *web admin UI*, used for exactly one setting: an OAuth2 authentication source's "map claimed groups to organization teams" field. Forgejo has **no REST API for authentication sources at all** (confirmed against the real swagger spec and a live instance — every path 404s); the only interfaces are this web form and the `forgejo admin auth update-oauth` CLI, and the CLI isn't reachable from an operator that only has a URL + HTTP credentials. `FirstOAuth2AuthSourceID` scrapes `/admin/auths`'s table for the first row whose Type column is "OAuth2" (the mapping is meaningless for LDAP/SMTP sources); `SetGroupTeamMap` scrapes the edit form at `/admin/auths/{id}`, resubmits every existing field verbatim (it's a full form POST, not a partial patch) with only `oauth2_group_team_map` overridden, and tells success (303) apart from a re-rendered validation error (200 + `.flash-error`). This is inherently coupled to Forgejo's HTML output; if it breaks, verify field names against a real instance the way this was built (see git history / PR description) rather than guessing.
- `internal/controller/instance.go` — shared helpers used by every reconciler: `resolveInstance` (look up the cluster-scoped `Forgejo` CR by name only) vs. `resolveOrganization`/`resolveRepository` (look up the namespaced `ForgejoOrganization`/`ForgejoRepository` CR by namespace *and* name — cluster-scoped vs. namespaced lookups take different arguments precisely because of the scope difference), `fetchSecretKey` (read one key out of a namespaced `Secret`), `fetchCredentials` (the username/password special case of that, for `AuthSecretRef`), `buildAPIClient`/`buildWebClient` (construct a `forgejoapi.Client`/`forgejoweb.Client` from those credentials).
- `internal/controller/fluxreceiver.go` — `resolveReceiverWebhookURL`, used only by `ForgejoWebhookReconciler`. Fetches a Flux `Receiver` via an `unstructured.Unstructured` client call against a hardcoded `notification.toolkit.fluxcd.io/v1, Kind=Receiver` GVK — deliberately *not* a typed client against the real `fluxcd/notification-controller` module, to avoid vendoring that module (and its own dependency tree) just for this one lookup; the CRD only needs to exist in the cluster, this operator doesn't own or manage it. Reads `status.webhookPath` and `spec.secretRef.name` off the unstructured object, then `fetchSecretKey`s the Secret that name points at (in the Receiver's own namespace, key `"token"` — Flux's own required key name) for the shared signing secret, and combines `status.webhookPath` with the target `Forgejo` instance's `spec.base` for the full URL.
- `internal/controller/status.go` — the `statusReady`/`statusError` constants every reconciler's `status.status` field uses (pulled out once `golangci-lint`'s `goconst` flagged the literals repeating across three controllers).
- `internal/controller/groupteammap.go` — `computeGroupTeamMap` lists every `ForgejoOrganization` across all namespaces (an unscoped `client.List`, so this deliberately doesn't stop at namespace boundaries — the mapping is instance-wide), keeps the ones targeting a given instance whose `DeletionTimestamp` is zero, and folds their `Teams[].Groups` into `group -> org -> [team, ...]` (keyed by `metadata.name`, not `namespace/name` — see the name-collision note above). `syncGroupTeamMap` pushes that through `forgejoweb`; finding no OAuth2 source is treated as a no-op, not an error (an instance may not have SSO configured yet).
- `internal/controller/forgejo_controller.go` — `ForgejoReconciler`: builds an API client, calls `GetVersion`, calls `ensureDefaultPullKeySecret`, and writes `status.version`/`status.status`/`status.message`. Requeues every 5 minutes (`forgejoReadyRequeueInterval`) to notice instance upgrades. RBAC needed is declared via `+kubebuilder:rbac:...` markers directly above `Reconcile`, turned into `config/rbac/role.yaml` by `make manifests` — note the secrets marker here specifically includes `create` (the other three controllers' secrets markers don't; `make manifests` unions verbs per group+resource across all markers repo-wide, so this is the only place `create` needs to be added for the merged `ClusterRole` to have it).
- `internal/controller/forgejoorganization_controller.go` — `ForgejoOrganizationReconciler`: uses the `forgejo.schranke.de/organization-finalizer` finalizer to delete the remote organization before the CR is removed (this cascades to its teams); creates the org if `GetOrg` 404s, otherwise calls `EditOrg`. `reconcileTeams` then diffs `spec.Teams` against `ListTeams`: creates/edits teams by name via `teamAccessArgs` (translates `AccessMode`/`RepoPermissions` into Forgejo's `permission`+`units_map` pair, defaulting unset `RepoPermissions` fields to `"none"`), deletes any existing team no longer in spec, and always leaves the built-in `"Owners"` team (`ownersTeamName`) untouched. On success (and again after remote deletion, so departing groups drop out promptly) it calls `syncGroupTeamMap`. Note: as of Forgejo 10, the edit-organization API applies `repo_admin_change_team_access` changes but **not** `visibility` changes — that's an upstream quirk, not a bug here.
- `internal/controller/forgejoactionsecret_controller.go` — `ForgejoActionSecretReconciler`: uses the `forgejo.schranke.de/actionsecret-finalizer` finalizer to delete the remote Actions secret before the CR is removed; resolves `OrganizationRef` → `ForgejoOrganization` (looked up in the `ForgejoActionSecret`'s own namespace, per `resolveOrganization(ctx, r.Client, actionSecret.Namespace, ...)`) → its `Forgejo` instance, reads the source `Secret` key, and calls `UpsertOrgActionSecret` unconditionally on every reconcile (safe/idempotent; there's no remote value to diff against).
- `internal/controller/forgejorepository_controller.go` — `ForgejoRepositoryReconciler`: same `resolveOrganization`(same-namespace)→`resolveInstance`→`buildAPIClient` chain and `forgejo.schranke.de/repository-finalizer` pattern as the action-secret reconciler, but `reconcileRemoteRepo` follows the organization reconciler's shape instead (`GetRepo` 404 → `CreateOrgRepo`, otherwise `EditRepo`) since, unlike Actions secrets, there's no single-call upsert for repositories. After that, `reconcileDefaultPullKey` (see `pullkey.go` above) ensures the instance's default pull key is added/removed per `spec.optOutDefaultPullKey`.
- `internal/controller/forgejowebhook_controller.go` — `ForgejoWebhookReconciler`: `resolveTarget` follows whichever of `spec.repositoryRef`/`spec.repository` is set to get an owner/repo pair and a resolved `Forgejo` instance (`parseRepositoryURL` extracts owner/repo from `spec.repository.url`'s path for the direct case), then `resolveReceiverWebhookURL` (see `fluxreceiver.go`) resolves the target URL/secret, then `reconcileRemoteHook` lists the repo's webhooks and matches by `config["url"]` to create-or-edit. Uses the `forgejo.schranke.de/webhook-finalizer` pattern; `reconcileDelete` tolerates the target repository already being gone (`forgejoapi.ErrNotFound` from `ListRepoHooks`) as nothing-to-clean-up rather than blocking deletion, same reasoning as the other reconcilers' "referenced parent already gone" handling.
- `cmd/main.go` — process entrypoint: builds the scheme, wires flags (metrics/health/leader-election/webhook TLS), constructs the `ctrl.Manager`, and registers all five reconcilers via `SetupWithManager`. New controllers/webhooks get registered here (look for the `+kubebuilder:scaffold:...` marker comments) — `operator-sdk create api` inserts at these markers automatically.
- `internal/webhook/v1alpha1/forgejoorganization_webhook.go` — `ForgejoOrganizationCustomValidator` (a `webhook.CustomValidator`, registered via `SetupForgejoOrganizationWebhookWithManager` in `cmd/main.go`). `ValidateCreate`/`ValidateUpdate` both call `checkForCollision`, which lists every `ForgejoOrganization` across all namespaces via `mgr.GetClient()` (the manager's cache-backed client — reads block until that GVK's informer has synced, no manual wait needed) and rejects if another object, in a *different* namespace, shares both `metadata.name` and `spec.instanceRef.name`. Comparing namespaces also correctly self-excludes the object being updated, since two live objects can never share both namespace and name. `ValidateDelete` is a no-op — deletion can't create a collision.
- `config/` — kustomize manifests consumed by `make install`/`make deploy`/`make build-installer`: CRDs (`config/crd`), RBAC (`config/rbac`), manager Deployment (`config/manager`), webhook (`config/webhook`, `config/certmanager`), and their composition (`config/default`). Most of this is generated or templated; hand-editing is normal only for `config/samples` and one-off kustomize patches. `config/certmanager` and the CA-injection `replacements` in `config/default/kustomization.yaml` are commented out by default (standard kubebuilder v4 scaffold) — the webhook's TLS cert has to come from somewhere for a real cluster deployment, envtest supplies its own self-signed one for tests, but production needs cert-manager enabled (uncomment `../certmanager` + the `CERTMANAGER`/webhook `replacements` blocks) or an equivalent. Two known scaffolding quirks in this repo, both from `operator-sdk create api`/`create webhook`: (1) it scaffolds a stray `_v1alpha1_<kind>.yaml` entry into `config/samples/kustomization.yaml` alongside the real one for every resource (file never actually created, would break `kustomize build config/samples`) — drop those bogus lines after running it again; (2) it drops the `namespaced: false` bookkeeping field from PROJECT for *every* existing resource, not just the new one, each time it's rerun — that field is cosmetic only (the real scope comes from each type's `+kubebuilder:resource:scope=Cluster` marker, unaffected), but restore it for accuracy.

**Toolchain note**: the module targets go1.25 (`go.mod`'s `go` directive, matching the Dockerfile's `golang:1.25` builder stage and `.devcontainer/devcontainer.json`'s image — keep those three in sync if this changes again). Watch out if bumping a dependency with `go get pkg@latest`: it can drag in transitive deps whose own `go.mod` requires a newer Go than the module currently targets, which force-raises this module's `go` directive too (Go's module graph pruning auto-raises it, but never auto-lowers it back on its own) — check `go list -m -f '{{.GoVersion}}' all` after any `go get`/`go mod tidy` if you want to confirm what actually moved.

## Distribution: Helm chart and CI

`dist/chart/` is **hand-written from scratch**, not generated by any kubebuilder/operator-sdk plugin — a first attempt via `kubebuilder edit --plugins helm/v2-alpha` (the `kubebuilder` CLI's chart-generation plugin; `operator-sdk` has no equivalent, only the unrelated `helm.sdk.operatorframework.io/v1` Helm-driven-operator plugin) was dropped entirely in favor of a minimal chart, deliberately omitting Prometheus/ServiceMonitor support, leader-election, and NetworkPolicies — none of which this operator needs. Don't reintroduce the plugin; edit the chart directly.

- `templates/rbac.yaml` — manager `ClusterRole`+`ClusterRoleBinding` (mirroring `config/rbac/role.yaml`'s rules) plus a metrics-auth `ClusterRole`+`ClusterRoleBinding` (`tokenreviews`/`subjectaccessreviews`, for the secure metrics endpoint). Always a `ClusterRole`, never namespaced — deliberately, since `Forgejo` is cluster-scoped and a `Role`/`RoleBinding` can never authorize access to a cluster-scoped resource no matter what rules it lists (this is exactly the bug found in the author's prior operator, whose chart had an `rbac.namespaced` toggle that silently produced a broken `Role` for cluster-scoped CRDs — no such toggle exists here).
- `templates/manager.yaml` — the manager `Deployment`, hardcoded to `replicas: 1` with no `--leader-elect` flag and no leader-election RBAC — safe only because there's exactly one replica; if that ever changes, leader-election needs to come back first.
- `templates/certificate.yaml` — self-signed cert-manager `Issuer`+`Certificate` producing the `webhook-server-cert` Secret that `templates/manager.yaml` mounts. **Not optional** — there is no `certManager.enabled` toggle; cert-manager must already be installed in the target cluster. Verified live (both here and in the author's prior operator, independently): without this, `helm install` leaves the manager pod stuck in `ContainerCreating` forever (`FailedMount ... secret "webhook-server-cert" not found`) — `helm lint`/`helm template` won't catch that, only a real install against a cluster with cert-manager present will.
- `templates/webhook.yaml` — the `ValidatingWebhookConfiguration`. Carries the `cert-manager.io/inject-ca-from` annotation pointing at the `Certificate` above; without it the apiserver never gets a `caBundle` and every admission request TLS-fails. This annotation is easy to forget (it was missing from the original plugin-generated chart too) and `helm lint`/`helm template` can't catch its absence — only a real admission request against a real cluster proves it's wired up (verified live: a `ForgejoOrganization` collision was actually rejected by the webhook, and unauthenticated metrics scraping returned a real `401`).
- `templates/crds/*.yaml` — copies of `config/crd/bases/*.yaml` with `helm.sh/resource-policy: keep` injected (so `helm uninstall` doesn't delete user data) — resync manually after changing an API type + running `make manifests`, there's no automation for this yet.
- `templates/_helpers.tpl` — `forgejo-operator.fullname` returns the release name as-is (no `<release>-forgejo-operator` suffixing). This chart assumes one install per cluster, so there's no nameOverride machinery — the simplification also fixes a real bug: the original plugin's longer naming scheme pushed names like `...-controller-manager-metrics-service` past Kubernetes' 63-character limit with the Makefile's own default release name `forgejo-operator`.
- `.github/workflows/` — `test.yml`/`lint.yml` are original to this project (Go tests, golangci-lint). `release.yml` (build+push image, package+push `dist/chart` on `v*.*.*` tags) and `test-chart.yml` (`helm lint`/`helm install` the chart against a throwaway Kind cluster, cert-manager installed first since it's a hard requirement) were copied over from another of the author's operators and had `sonarqube-operator` naming leftovers fixed to `forgejo-operator`/`forgejo-operator-system`; the Prometheus/ServiceMonitor steps present in that original were deleted outright (not just left commented) since this chart has no such support.

## Testing

`internal/controller/suite_test.go` boots two real backends per test run, no mocking of Forgejo:

1. `envtest` — a real kube-apiserver + etcd (no kubelet/scheduler) for the Kubernetes side. `CRDDirectoryPaths` includes both `config/crd/bases` (this operator's own CRDs) and `internal/controller/testdata` — the latter holds a minimal stand-in `notification.toolkit.fluxcd.io_receivers.yaml` CRD (loose, `x-kubernetes-preserve-unknown-fields` schema) so the apiserver has something to validate/store test `Receiver` objects against, without this operator depending on the real `fluxcd/notification-controller` module (see `fluxreceiver.go` above).
2. A real Forgejo server via `testcontainers-go` (`startForgejoContainer`), image `codeberg.org/forgejo/forgejo:10`, sqlite backend, install-lock pre-set via env vars, **SSH enabled** (port `22/tcp` exposed, waited on via `wait.ForListeningPort` alongside the usual HTTP readiness check — needed for the default-pull-key tests, which do a real SSH host-key handshake against it). After the container is healthy, an admin user *and* a test OAuth2 auth source (`execAsGit`, provider `github` — needs no reachable discovery URL, unlike `openidConnect`) are provisioned via `container.Exec(..., tcexec.WithUser("git"))` — the image refuses to run as root, so the exec user must be set explicitly. All of this is shared across every spec in the suite (`forgejoBaseURL`/`forgejoAdminUsername`/`forgejoAdminPassword`/`forgejoOAuth2SourceID`/`forgejoSSHHost`/`forgejoSSHPort` package vars, the OAuth2 source ID always `1` since it's the only one ever created) and torn down in `AfterSuite`.

`forgejo_controller_test.go`, `forgejoorganization_controller_test.go`, `forgejoactionsecret_controller_test.go`, `forgejorepository_controller_test.go`, and `forgejowebhook_controller_test.go` assert against this real server directly (via a second `forgejoapi.Client` built in the test) rather than only checking CR status — e.g. the organization/repository tests confirm the org/teams/repo actually exist/are gone on the Forgejo server, and the action-secret tests confirm the secret name appears/disappears from `ListOrgActionSecrets` (its value can never be asserted — the real API is write-only). The default-pull-key specs (in both of those files) generate a real secret against the real container and then really SSH-authenticate a deploy key against it, rather than just checking the Secret's shape. `groupteammap_test.go` goes one step further: since there's no REST API to read back an auth source's config, `readStoredGroupTeamMap` execs `sqlite3` inside the container to read `login_source.cfg` directly and asserts on the decoded JSON. `forgejowebhook_controller_test.go`'s `createTestReceiver` builds a real Flux `Receiver` against envtest as an `unstructured.Unstructured` (see `fluxreceiver.go`), setting `status.webhookPath` via a separate `Status().Update` call since it's a status subresource; its tests also double as a live check that the CRD's `+kubebuilder:validation:XValidation` exactly-one-of rule is actually enforced by a real apiserver, not just present in the Go struct tag. This means `make test` requires a working Docker daemon; there's no fallback/skip path.

`internal/webhook/v1alpha1/webhook_suite_test.go` is a **separate** envtest suite (its own `TestAPIs`/`RunSpecs`, own manager, own `k8sClient`) from `internal/controller`'s — it sets `envtest.Environment.WebhookInstallOptions.Paths` to `config/webhook`, which makes envtest generate a self-signed cert and install the real `ValidatingWebhookConfiguration`, then starts an actual manager/webhook server bound to `WebhookInstallOptions.LocalServingHost/Port` and waits for a TLS handshake to succeed before running specs. `forgejoorganization_webhook_test.go` then just does plain `k8sClient.Create`/`Update` calls — those go through the *real* admission chain over TLS, not a direct call to the validator's Go methods. It needs no Forgejo container at all (the collision check never talks to Forgejo), so it's much faster than the controller suite. envtest doesn't run the namespace controller, so a deleted `Namespace` stays stuck `Terminating` forever — the tests avoid that entirely by giving every spec its own freshly created namespace and instance name (via `nextTestID()`) rather than deleting and reusing fixed ones.

There is no `test/e2e/` — a prior scaffolded Kind-based e2e suite was dropped as redundant with the real-Forgejo-container tests above, and `.github/workflows/test-chart.yml` (Helm chart lint/install against a Kind cluster) covers the "does this actually deploy" question separately. Don't re-add a `make test-e2e` target without checking whether the thing it would test isn't already covered by `make test`.

## Linting notes

`golangci.yml` enables `dupl` and `lll` (line length) globally but excludes them for `internal/*`; `lll` is also excluded for `api/*`. `revive` is configured with `comment-spacings` and `import-shadowing` rules — keep new code consistent with those.
